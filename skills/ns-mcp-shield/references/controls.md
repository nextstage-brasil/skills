# Secure MCP controls (1–8)

Apply these when designing or hardening an MCP server. For review findings, map each gap to a risk in `vulnerability-landscape.md`.

## 1. Secure MCP architecture

**Local vs remote connections**

- **Local servers:** prefer STDIO or Unix sockets over network sockets. If local HTTP is required: bind only to `127.0.0.1`, still require explicit authentication/authorization, and validate the `Origin` header. Run in isolated/sandboxed subprocesses or containers with minimal privileges and minimal or no external network access.
- **Remote servers:** enforce TLS 1.2+ on all connections. Strictly validate every JSON-RPC message against the MCP schema; reject malformed or unrecognized data.

**Trusted connections and client authentication**

- Known static relationships: allowlists, hardcoded connections or mutual TLS (mTLS).
- Dynamic environments: strong authentication (OAuth 2.1 / OIDC) to verify client identity — never rely on static network trust alone.

**Isolate users and sessions** (multi-tenant)

- Strictly segregate execution contexts, memory and temp storage per user/agent.
- Never store user-specific data in global variables, class-level attributes or shared singletons. Instantiate separate objects per session, or use a strictly session-keyed state store (e.g. Redis with `session_id` namespaces).
- **Deterministic lifecycle cleanup:** when a session terminates, disconnects or times out, immediately flush and destroy its file handles, temp storage, in-memory context and cached tokens.
- **Per-session resource quotas:** limits on memory, CPU, file system and API rate, keyed to session ID or user identity.

## 2. Safe tool design

- **Cryptographic tool manifests:** every tool has a signed manifest with description, schema, version and required permissions; verify signature and hash at load time.
- **Strict onboarding and approval:** formal approval workflow for adding or updating any tool description or functionality — SAST, dynamic testing, dependency scanning (SCA) and manual security review.
- **Validate descriptions vs. behavior:** manual checks, tool pinning and LLM scans to ensure advertised functionality matches runtime behavior. Flag any tool that performs actions (e.g. network writes) not mentioned in its description.
- **Tool structure validation:** maintain and audit every field of each tool. Expose only minimal, strictly necessary fields to the model; keep internal metadata and sensitive fields out of model context.

## 3. Data validation & resource management

- **Resource usage limits:** quotas and rate limits on tool invocations and data fetches per session; timeouts and isolated memory/compute budgets against DoS and runaway processes.
- **Strict input/output validation:** treat all data as untrusted. Define and enforce JSON Schemas for every tool's inputs (from the model) and outputs (back to the model). Reject any request that does not match.
- **Sanitization and encoding:** filter and sanitize inputs to the model and outputs into the tool; strip or escape sequences that enable classic injection (XSS, SQL injection, RCE). Enforce size limits on all outputs from tools or model.

## 4. Prompt injection controls

- **Structured tool invocation:** favor schema-validated structured JSON tool calls over free-form text commands generated by the model.
- **Human-in-the-loop (HITL):** for high-risk actions (deleting data, sending money, system-level changes) pause and require explicit human confirmation on the MCP client (e.g. MCP elicitations) before proceeding.
- **LLM-as-a-judge:** for high-risk actions, run an approval check in a separate LLM session with a policy prompt defining which tool calls and parameters are allowed or blocked.
- **One task, one session:** reset MCP sessions when the agent switches context or task, so hidden instructions do not persist in long histories (also reduces context degradation).

## 5. Authentication & authorization

- **OAuth 2.1 / OIDC is mandatory for all remote MCP servers.** Validate `iss`, `aud`, `exp` and the signature on every request.
  - **Token delegation:** use OAuth token exchange (RFC 8693) to pass user context and permissions while limiting permissions and keeping the server's own non-human identity (NHI).
  - **Prohibit token passthrough:** never forward client tokens to downstream APIs. Use tokens issued to the MCP server or validated via On-Behalf-Of flows. Passthrough breaks audit trails, bypasses policy and creates a confused deputy risk.
- **Short-lived, scoped tokens:** lifetimes in minutes, narrow scopes; revalidate signature, audience and expiry before executing any tool or resource access.
- **Sessions are state, not identity:** never authenticate or authorize by session ID alone. Bind every session/stream/queue entry to validated user and client identity, rotate/expire aggressively, re-check authorization before sensitive actions.
- **Centralized policy enforcement:** a dedicated policy/gateway layer enforces authentication, authorization, consent, tool filtering and audit logging, consistently across agents, servers and upstream services.

## 6. Secure deployment & updates

- **Secrets management:** secrets in a vault — not in environment variables, logs or plaintext code. The LLM never has access to a secret; secret handling lives in transparent middleware the LLM cannot reach.
- **Containerize and harden:** minimal hardened container, non-root user, drop unnecessary packages, dependencies and Linux capabilities.
- **Network segmentation:** restricted segment; firewall rules / Kubernetes NetworkPolicies block all inbound and outbound traffic except what is explicitly required.
- **Supply chain controls:** version-pin and scan dependencies at build time, signed container images, monitor new CVEs, maintain AIBOMs for provenance and tamper detection.
- **CI/CD security gates:** fail the build on new vulnerabilities, unapproved dependencies or policy-check failures (policy-as-code, e.g. OPA).
- **Safe error handling:** never return stack traces, tokens, filesystem paths or tool internals to the model/client.

## 7. Governance

- **Cryptographic integrity:** signing and version pinning for all tools, dependencies and registry manifests.
- **Peer review and oversight:** no new tool or major change goes live without a security-focused peer review.
- **Audit logs and trails:** log every action — tool invocations with parameters, resource access, authn/authz events, configuration changes (old and new values). Use field-level allowlists and redaction/hashing to keep sensitive data out of logs. Store logs securely and immutably for forensics.
- **Non-human identity governance:** every agent, backend process and MCP server is a first-class identity with unique credentials and tightly scoped permissions; continuously audit their data access and tool usage.

## 8. Tools & continuous validation

- **Automated code scanning:** SAST (with custom MCP rules) and MCP-specific scanners (e.g. Invariant MCP-Scan) in CI; SCA (e.g. npm audit, pip audit, OSV-Scanner) for dependencies. Break builds that exceed risk tolerance.
- **Runtime protections:** enforce isolation with seccomp profiles, AppArmor or specialized wrappers (e.g. context-protector); monitor runtime behavior (e.g. mcp-watch).
- **Continuous monitoring:** feed audit logs to a SIEM; real-time alerts for spikes in failed validations, high-frequency tool calls, or tools suddenly accessing unusual files.
- **Supply chain vigilance:** evaluate posture with OpenSSF Scorecard; monitor OSV for new dependency issues.
