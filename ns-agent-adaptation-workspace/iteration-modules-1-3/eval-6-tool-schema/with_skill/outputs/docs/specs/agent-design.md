## Problem statement

Internal warehouse-ops agent must answer fulfillment questions that today require two admin UIs. Initial tool draft exposed **two tools both named `search`**, each accepting free-text `status`. That design causes wrong-tool selection and wrong-arg API failures. Objective: lock typed tool inventory before any framework work.

## Evaluation criteria

| Criterion | Target |
| --------- | ------ |
| Golden set | 30 NL cases covering order-only, inventory-only, and dual-domain queries |
| Functional pass rate | ≥ 90% (correct tool, correct enum filter, no hallucinated IDs) |
| Usefulness | Synthesized answer, not raw JSON |
| Business metric | Mean time to answer < 30 s (baseline ~4 min across two UIs) |

## Failure diagnosis (info vs behavior)

| Type | Evidence |
| ---- | -------- |
| **Information** | Model lacks live WMS order and lot data |
| **Behavior** | Generic `search` names collide; free-text `status` rejected by API |
| **Classification** | **both** |

Implication: live read tools required (not RAG-only); schema fixes required before Fine-Tune.

## Agent justification (or explicit non-agent decision)

**Agent required.** Staff questions arbitrarily combine order tracking and stock lookup. No fixed pipeline covers all phrasings. Two read tools with plan-first validation suffice for MVP; no Write actions in scope.

### Typed schemas (locked)

#### `search_fulfillment_orders`

**Description:** Look up customer fulfillment orders by ID, customer, SKU, or date range; filter by fulfillment lifecycle status. Not for warehouse lot/bin quantities or stock-on-hand.

**Arguments:**

| Arg | Type | Required | Notes |
| --- | ---- | -------- | ----- |
| `order_id` | string | no | Exact order ID |
| `customer_id` | string | no | Customer identifier |
| `sku` | string | no | Product SKU |
| `date_from` | string (ISO date) | no | Range start |
| `date_to` | string (ISO date) | no | Range end |
| `fulfillment_status` | enum | no | `pending_pick` \| `packed` \| `shipped` \| `delivered` \| `cancelled` \| `returned` |

**Return:** `{ orders: [{ order_id, customer_id, sku, qty, fulfillment_status, promised_ship_date }], total_count: number, not_found: boolean }`

Empty lookup: `{ orders: [], total_count: 0, not_found: true }`

#### `search_warehouse_inventory_lots`

**Description:** Look up warehouse inventory lots by SKU, lot_id, aisle, or bin; filter by lot availability status. Not for customer order tracking or shipment state.

**Arguments:**

| Arg | Type | Required | Notes |
| --- | ---- | -------- | ----- |
| `sku` | string | no | Product SKU |
| `lot_id` | string | no | Lot identifier |
| `aisle` | string | no | Warehouse aisle |
| `bin` | string | no | Bin location |
| `lot_status` | enum | no | `available` \| `reserved` \| `quarantine` \| `expired` |

**Return:** `{ lots: [{ lot_id, sku, aisle, bin, qty_on_hand, lot_status, expires_on }], total_count: number, not_found: boolean }`

Empty lookup: `{ lots: [], total_count: 0, not_found: true }`

### Name disambiguation note

Original names (`search`, `search`) failed disambiguation against the bound tool set. Locked names are domain-specific per `tool-schema-design.md`: generic `search` + similar sibling = selection collision.

### Enum demand note

Original free-text `status` on both tools replaced with **distinct** closed enums — order lifecycle vs lot availability are different domains and must not share one `status` field.

## Planning contract

- **Plan ≠ execute:** emit tool list + parameter values before any call
- **Validate before run:** tool names ∈ `{search_fulfillment_orders, search_warehouse_inventory_lots}`; enum args ∈ declared sets
- **Parameter reporting:** plan surfaces `fulfillment_status` / `lot_status` values explicitly
- **Reflection:** skip for MVP (read-only, short plans)

## Memory design

| Tier | What stored | Why |
| ---- | ----------- | --- |
| Internal weights | base model | general NL; no Fine-Tune yet |
| Context window (short-term) | current thread, plan, tool results | working state per question |
| Episodic (external) | optional audit log of tool calls | compliance trace; truncate by policy |
| Semantic (external) | none | no user profile or durable facts needed |

**Retention:** no long-term semantic memory — valid design; reduces compliance liability.

## Evaluation plan (agent metrics)

| Metric | Purpose |
| ------ | ------- |
| `wrong_tool_rate` | order vs inventory mis-route |
| `argument_accuracy` | enum args valid vs golden |
| valid plan % | schema validation pass before execute |
| p95 latency | vs 30 s SLA |
| cost per resolved question | vs baseline staff time |

Separate planning failures (bad plan) from tool failures (bad args / API errors).

## Guardrails & observability

| Layer | Control |
| ----- | ------- |
| Input | block bulk PII export patterns |
| Output | answers must cite IDs present in tool results only |
| Logs | tool name, enum args, latency, `not_found`, errors |
| Alerting | `wrong_tool_rate` > 5% → MTTD investigation |

## Risks (compounding errors, write tools)

| Risk | Mitigation |
| ---- | ---------- |
| Third search-like tool added with generic name | Rename against full bound set; prefer fewer tools |
| WMS adds new status value | version enum; re-run golden set |
| Dual-domain questions over-call APIs | plan validation caps max two reads per turn |
| Compounding error on longer plans | MVP limits to ≤2 steps |

No Write tools in MVP — no irreversible side-effect risk.
