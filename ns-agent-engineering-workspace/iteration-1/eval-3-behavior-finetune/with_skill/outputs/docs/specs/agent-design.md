## Problem statement

The foundation model already returns factually correct content grounded in product docs, but responses frequently violate the required JSON schema and ignore the brand tone guide. Stakeholders asked whether to build an Agent. Goal: deliver a single-shot path from user question (+ optional session context) to one schema-valid, tone-aligned JSON answer while preserving current factual accuracy. Constraints: no framework choice, no implementation, Agent only if ladder-justified.

## Evaluation criteria

Success is locked before any adaptation beyond diagnosis:

1. **Functional correctness (schema):** binary JSON Schema (or equivalent contract) validation on every response. Target usefulness threshold: high pass rate on a golden set (design intent ≥ 95%).
2. **Tone rubric:** graded checks against the tone guide (banned slang, required register, empathy markers where specified). Target: meet agreed pass threshold on the same golden set.
3. **Factual parity:** answers remain as correct as today’s doc-grounded baseline (no regression on fact checks / citation agreement).

Business link: reduce human rewrite and support-QA rework caused by malformed payloads and off-tone copy. Usefulness is explicit: ship only when schema + tone thresholds hold without fact regression.

## Failure diagnosis (info vs behavior)

**Classification: behavior.**

Evidence from opening context: facts from docs are already right; remaining failures are wrong JSON shape and ignored tone guide — classic instruction-following / format / domain-style gaps.

Implications:

- Not an information gap → RAG is not the primary fix.
- Not a multi-step decide-act loop → Agent is not the primary fix.
- Ladder points to **Prompt**, then **Fine-Tune** if Prompt is exhausted.

## Adaptation path (locked ladder decisions)

| Gate | Decision | Rationale |
| ---- | -------- | --------- |
| Evaluation | locked | Schema pass, tone rubric, factual parity defined before heavier adaptation |
| Prompt | required next; exhaust first | In-context schema, few-shots, tone constraints, negative examples — cheapest reversible lift |
| RAG | not primary | Failures are not missing private/recent knowledge; facts already OK |
| Agent | rejected (primary) | No need to perceive/decide/act with tools beyond single-shot generation; Agent adds compounding error |
| Fine-Tune | yes after Prompt exhausted | Behavior-based format + tone stickiness after Prompt plateaus |

## Agent justification (or explicit non-agent decision)

**Explicit non-agent decision.**

Agent is not justified. The system does not need environment perception, multi-tool decisioning, write-side effects, or outcome-driven replanning as the primary remedy. The model already has the right facts; it fails at emitting the contracted shape and following the tone guide.

Primary path: **Prompt → Fine-Tune** (Fine-Tune only after Prompt exhaustion is measured). Optional: treat schema/tone snippets as Prompt material — not as an information-RAG product. Do not substitute an Agent “validate-and-retry” loop for instruction-following adaptation; that masks Prompt/Fine-Tune debt and raises cost, latency, and compounding error without addressing the root behavior gap.

## Guardrails & observability

**Output Guardrails**

- Hard gate: reject or quarantine schema-invalid outputs before client delivery.
- Tone: score against locked rubric; fail or flag below threshold per product policy.
- Do not invent Agent write tools to “fix” bad shape.

**Input Guardrails**

- Bound prompt inputs; keep schema version and tone-guide version pinned in the request path.

**Observability (MTTD/MTTR)**

- Log: prompt artifact version, Fine-Tune artifact/version (if any), model id, schema pass/fail (+ failing paths), tone rubric scores, golden-set deltas over time.
- Separate failure classes: `schema_*` vs `tone_*` vs `fact_regression` so Prompt vs Fine-Tune decisions stay evidence-based.
- MTTD: alert on schema/tone pass-rate drops vs baseline. MTTR: roll back prompt or Fine-Tune artifact to last green golden run.

## Risks (compounding errors, write tools)

| Risk | Mitigation |
| ---- | ---------- |
| Jumping to Agent for format/tone | Lock non-agent path; require Evaluation + Prompt exhaustion before any Agent revisit |
| Fine-Tune before Prompt measured | Run Prompt A/B on golden set; Fine-Tune only if thresholds miss |
| Schema drift vs tone-only Fine-Tune | Co-train / co-evaluate both schema and tone; keep fact checks in harness |
| Silent fact regression after Fine-Tune | Keep factual parity checks in CI golden set |
| Soft “repair loops” that become de-facto Agents | Prefer hard schema gate + better generation; no multi-step tool planner in MVP |
