## Problem statement

Support needs an automated refund-triage flow: look up a customer’s order via SQL, decide whether a refund applies under policy, then notify the customer by email. The flow is multi-step. Email must never send without human approval. Payment/ledger mutation is out of scope for this design. Stakeholders are support operators and customers receiving eligibility outcomes.

## Evaluation criteria

A run is successful only if all of the following hold:

1. **Order-fact correctness** — SQL lookup returns the order snapshot that matches the gold ticket’s expected fields (status, dates, amounts, customer match).
2. **Policy-rubric match** — eligibility decision matches a gold policy rubric for that snapshot (eligible / ineligible + cited basis).
3. **Email consistency** — draft content agrees with the decision (no “approved” wording on ineligible cases).
4. **Write safety** — any unapproved `send_customer_email` is a **hard fail**.
5. **Usefulness threshold** — ≥ **90%** rubric pass on a held-out refund-ticket gold set.

**Business link:** reduce average refund-ticket handle time without increasing wrongful-refund (or wrongful-denial) rate versus the current manual baseline.

## Failure diagnosis (info vs behavior)

**Classification: both** (information-primary + control/behavior across steps).

- **Information:** Live order state and private policy details are not in model weights; inventing delivery dates or window rules without tools is an information failure.
- **Behavior / control:** Multi-step instruction following, especially never sending mail without approval and aligning draft tone/content to the decision, is a behavior and Guardrails concern — not fixed by retrieval alone.

Implication: RAG (or read tools) address the info gap; Agent + HITL address decide-and-act. Fine-Tune is not the first lever.

## Adaptation path (locked ladder decisions)

| Gate | Decision | Rationale |
| ---- | -------- | --------- |
| Evaluation | locked | Gold rubric + ≥90% usefulness + unapproved send hard fail before any adaptation choice |
| Prompt | support only — not sufficient | Policy and draft style belong in context; Prompt cannot perceive DB or execute mail |
| RAG | partial — information help | Policy corpus / history retrieval; does not replace multi-step tool act |
| Agent | **locked — required** | Perceive (SQL) → decide eligibility → act (email) with outcome feedback and HITL |
| Fine-Tune | deferred (out of MVP) | Attack behavior gaps with Prompt + Guardrails first; revisit if eval plateaus |

## Agent justification (or explicit non-agent decision)

**Agent is required.** The product must (1) perceive environment state via SQL, (2) decide eligibility under policy, (3) act with a Write tool (email) under approval, and (4) branch on tool outcomes (abort vs send). A Prompt-only or RAG-only path cannot own the gated write or the multi-step tool loop. A deterministic single-shot “classify then one API call” underfits policy judgment over fresh order facts and approval gates. Explicit **non-agent rejection**: Prompt / RAG / single-shot tool are insufficient for the locked objective.

## Tool inventory (taxonomy tagged)

| Tool | Purpose | Category | Safety (if Write) |
| ---- | ------- | -------- | ----------------- |
| `lookup_order_sql` | Read order/customer facts needed for eligibility | Capability extension | Read-only DB credentials; no schema writes |
| `fetch_refund_policy` | Retrieve applicable refund policy / window rules | Knowledge augmentation | Read-only corpus; no side effects |
| `send_customer_email` | Deliver eligibility outcome to the customer | Write actions | **HITL approval required**; confirm params (to, subject, body) before execute; no send without approval token |

MVP caps at these three tools. Payment capture, ledger update, and CRM ticket create are deferred.

## Planning contract

- **Plan ≠ execute.** Agent emits a short plan before tool calls: lookup order → (optional) fetch policy → decide eligibility → draft email → await HITL → send or abort.
- **Validate before run:** schema of allowed tools, step budget, policy constraints (e.g. send cannot precede lookup/decide), no illegal tool order.
- **Parameter reporting:** Before any Write, surface concrete email parameters for human review.
- **Parallel plans + judge:** Optional later; not required for MVP — single short plan + validator preferred to limit compounding error.
- Long open-ended plans are disallowed; prefer checkpoints at decision and before Write.

## Memory design

| Tier | What stored | Why |
| ---- | ----------- | --- |
| Internal weights | General language and reasoning only; no customer PII or order facts | Avoid baking private/fresh data into the model; Fine-Tune not justified yet |
| Context window (short-term) | Current ticket ids, plan, SQL results, scratch decision, email draft | Working state for this session only |
| External (long-term / RAG) | Orders DB via `lookup_order_sql`; policy corpus / ticket history via `fetch_refund_policy` | Durable and fresh facts must be re-fetched / retrieved, not “remembered” |

## Evaluation plan (agent metrics)

Separate **planning failures** (bad decomposition, illegal tool order, missing HITL step) from **tool failures** (wrong tool, wrong args, SQL miss, mail API flake).

| Metric | Target / note |
| ------ | ------------- |
| Valid plan % | Plans passing schema/policy validator before execute |
| Steps per success | Prefer shorter plans if rubric quality holds |
| Cost per task | Tokens + tool cost vs Prompt+RAG baseline |
| Latency p50/p95 | Vs same baseline |
| Task success / rubric pass | From Evaluation criteria (≥90% gold set) |
| Write safety | Unapproved send count = 0 (hard fail any violation) |

Baseline: Prompt + policy RAG without Agent tool loop, measured where comparable (decision quality only — baseline cannot safely send mail).

## Guardrails & observability

**Input Guardrails:** Accept known ticket/order/customer identifiers; sanitize free-text reason for injection; reject requests missing required ids.

**Output Guardrails:** `send_customer_email` blocked without prior approval event; drafts must not claim refund completed if decision is ineligible; PII redaction in shared logs as required by policy.

**Observability (MTTD/MTTR):** Persist trace with plan text, tool names/args (redacted), SQL result hashes or field summaries, decision + rubric scores, approval actor/timestamp, send vs abort. Alert on any Write invocation lacking approval linkage. Goal: distinguish planning vs tool vs policy failure within one incident review.

## Risks (compounding errors, write tools)

| Risk | Mitigation |
| ---- | ---------- |
| Compounding error across lookup → decide → write | Short plans, validate-before-run, mid-flow checkpoints |
| Wrongful eligibility / bad customer message | Gold rubrics, policy RAG, human review of decision+draft |
| Accidental or injected send | HITL + param confirm; approval token; alert on ungated Write |
| Over-tooled MVP | Cap at three tools; defer payments and CRM writes |
| Stale “remembered” order state | Always re-query SQL; no durable order facts in weights |
